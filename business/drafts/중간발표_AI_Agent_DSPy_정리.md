# 중간발표 참고자료: AI·Agent·Skill 활용 및 DSPy 설명

## 0. 발표에서 먼저 구분하면 좋은 점

PULSE에서 말하는 AI 활용은 두 층으로 나누어 설명하는 것이 안전합니다.

1. 개발 과정에서의 AI/Agent 활용
   - 팀원이 의도를 자연어로 설명하면 Agent가 코드 탐색, 초안 작성, 구현, 반복 검증을 보조했습니다.
   - 즉, “바이브코딩” 방식으로 개발 속도를 높였지만, 최종 방향 결정과 검수는 사람이 했습니다.
   - 여기에 프로젝트 전용 custom skill, 기존 범용 skill, Playwright MCP, 서브 에이전트 방식의 역할 분리까지 함께 활용했습니다.

2. 서비스 내부 기능에서의 AI 활용
   - PULSE 제품 안에서는 리뷰 분석, 페르소나 생성, 리뷰 답변 생성, 홍보영상 프롬프트/영상 생성에 AI가 쓰였습니다.
   - 특히 DSPy는 홍보영상 생성 로직에서 프롬프트를 더 일정한 구조로 만들기 위한 최적화 계층으로 설계되었습니다.

## 1. 우리가 AI를 실제로 어디에 썼는지

### 1-1. 문서 정리

사용했습니다.

프로젝트 설명서, 사업계획서 초안, R&D 확장 아이디어, 증빙자료 구성처럼 글의 흐름을 잡아야 하는 문서 작업에 Agent를 활용했습니다. 사람이 핵심 방향과 사실관계를 주면 Agent가 초안을 구조화하고, 발표나 제출 문서에 맞게 문단 순서와 표현을 정리했습니다.

발표용 문장:

> “AI를 문서 작성자처럼 쓴 것이 아니라, 흩어진 기획 내용과 코드 구현 상태를 빠르게 정리하는 보조 편집자로 활용했습니다.”

실제 예시:

- 사업계획서와 아이디어 문서의 구조 정리
- 제출용 증빙자료의 붙임 순서 정리
- 프로젝트 브리프와 작업 로그 기반 현황 요약
- HWPX 스킬과 DOCX 변환 스크립트를 통한 발표 참고 문서 생성 자동화

### 1-2. 기능 기획

사용했습니다.

PULSE는 화면이 많고 기능 흐름이 길기 때문에, Agent를 기획 회의의 보조자처럼 사용했습니다. “손님 분석 결과에서 홍보영상 만들기로 넘어갈 때 어떤 정보가 전달되어야 하는가?”, “자동 프롬프트가 언제 다시 생성되고 언제 멈춰야 하는가?” 같은 조건을 정리하는 데 활용했습니다.

발표용 문장:

> “기능을 바로 코딩하기 전에 Agent와 먼저 사용자 흐름, 예외 상황, API 계약을 정리해서 구현 방향을 좁혔습니다.”

실제 예시:

- 손님 분석에서 선택한 페르소나를 홍보영상 생성 화면으로 전달
- 사이드바 이동 시 오래된 navigation parameter가 남지 않도록 규칙 정리
- AI 자동 프롬프트가 페르소나, 스타일, 품질 모드, 업로드 이미지 변화에 반응하도록 설계
- 사용자가 직접 프롬프트를 수정하면 자동 모드가 꺼지도록 UX 조건 정리

### 1-3. 코드 탐색

사용했습니다.

프론트엔드, Spring Boot, FastAPI가 분리되어 있어 특정 기능을 수정하려면 세 저장소의 연결 지점을 빠르게 찾아야 했습니다. Agent는 검색과 파일 읽기를 통해 “어느 화면이 어느 API를 부르고, 그 API가 어떤 서비스로 이어지는지”를 추적하는 데 도움이 됐습니다.

발표용 문장:

> “Agent를 코드베이스 내비게이터처럼 사용해서, 여러 모듈에 흩어진 기능 흐름을 빠르게 파악했습니다.”

실제 예시:

- `pulse_FE`의 홍보영상 화면에서 FastAPI 프롬프트 추천 API 호출 흐름 확인
- `pulse_python`의 `/api/info/prompt-recommendation`, `/api/info/generate`, `/api/info/status/{task_id}` 흐름 확인
- `pulse_spring`의 리뷰 관리 API가 FastAPI 답변 생성 API로 이어지는 구조 확인
- 실제 구현과 문서 내용이 충돌할 때 코드 기준으로 상태 재확인

### 1-4. 코드 제작

사용했습니다.

Agent는 단순 코드 자동완성보다 넓은 범위에서 사용했습니다. 요구사항을 자연어로 설명하면 관련 파일을 찾아 수정하고, 필요한 경우 프론트엔드·백엔드·AI 서버의 데이터 형태를 맞추는 식으로 작업했습니다. 이 과정이 우리가 말하는 바이브코딩에 가장 가깝습니다.

발표용 문장:

> “우리는 Agent에게 단순 함수 한 줄을 맡긴 것이 아니라, ‘이 기능이 이렇게 동작해야 한다’는 의도를 전달하고 관련 코드 수정과 검증을 함께 반복했습니다.”

실제 예시:

- 회원가입·로그인 후 분석 작업 ID를 저장하고 손님 분석 화면과 연결
- 리뷰 관리 화면에서 실제 네이버/카카오 리뷰 데이터를 보여주도록 mock 제거
- 선택한 리뷰 카드 기준으로 AI 답변이 생성되도록 상태 흐름 수정
- 홍보영상 생성에서 페르소나·스타일·품질 모드·이미지를 반영한 프롬프트 추천 API 연결
- Veo/Gemini/Vertex AI 관련 오류를 숨기지 않고 명확히 보여주도록 예외 처리 개선

### 1-5. 반복 작업 자동화

사용했습니다.

반복되는 검증, 문서 생성, 환경 점검, 스모크 테스트 같은 작업을 Agent와 스크립트로 정리했습니다. 이 부분은 개발 속도뿐 아니라 실수 감소에도 도움이 됐습니다.

발표용 문장:

> “반복 검증과 문서 산출처럼 사람이 매번 손으로 하면 실수하기 쉬운 작업을 Agent와 스크립트로 자동화했습니다.”

실제 예시:

- 프론트엔드 lint/build, Spring build, Python test, Playwright smoke 흐름 정리
- 브라우저 E2E로 회원가입, 로그인, 분석 조회, 리뷰 답변 생성, 템플릿 CRUD 확인
- 사업계획서·증빙자료용 이미지와 문서 생성 스크립트 관리
- HWPX 스킬을 추가해 한글 문서 생성과 구조 검증 자동화

### 1-6. Git 작업 보조

사용했습니다.

PULSE는 메인 repo와 서브모듈이 함께 있는 구조라 Git 상태 확인이 복잡합니다. Agent를 통해 변경 파일 확인, 서브모듈 상태 점검, 커밋 범위 정리, 작업 로그 작성 같은 부분을 보조했습니다.

발표용 문장:

> “Git에서는 Agent를 커밋 자체를 대신 판단하는 도구가 아니라, 변경 범위와 서브모듈 상태를 빠르게 정리해주는 보조자로 사용했습니다.”

실제 예시:

- 메인 repo와 `pulse_FE`, `pulse_spring`, `pulse_python`의 변경 상태 구분
- 서브모듈 참조 업데이트 누락 여부 확인
- 작업 로그 작성으로 어떤 기능을 검증했는지 기록
- 커밋 전 변경 범위와 검증 결과 정리

### 1-7. Skill, MCP, 서브 에이전트 활용

사용했습니다.

Agent를 그냥 한 번씩 대화하는 도구로만 쓰지 않고, 반복되는 작업은 skill과 MCP, 역할 분리 방식으로 정리했습니다. 이 부분은 발표에서 “AI를 도구처럼 체계화해서 썼다”는 근거가 됩니다.

#### custom skill

custom skill은 우리 프로젝트에 맞춘 작업 매뉴얼입니다. Agent가 매번 처음부터 상황을 해석하지 않도록, PULSE의 문서 작성 규칙, Git 규칙, 제안서 작성 규칙, HWPX 처리 규칙을 skill로 저장했습니다.

실제 사용/구성 예시:

- `yec-proposal-planner`: 예비창업패키지식 사업계획서 구조 정리
- `appendix-evidence-packager`: 증빙자료 제출 순서와 붙임 라벨 정리
- `proposal-visual-png`: 사업계획서용 PNG 도식 생성
- `korean-docx-safe-builder`: 한글 DOCX 생성 시 인코딩 깨짐과 Word 잠금 문제 방지
- `hwp-hwpx`: HWP/HWPX 문서 읽기, 변환, 검증을 위해 새로 만든 custom skill

발표용 문장:

> “저희는 Agent에게 매번 같은 설명을 반복하지 않기 위해, PULSE 프로젝트 전용 custom skill을 만들어 문서 작성, 증빙 정리, HWPX 처리, Git 운영 규칙을 재사용했습니다.”

#### 미리 만들어진 skill

미리 만들어진 skill은 범용 작업을 빠르게 수행하기 위한 기본 도구처럼 사용했습니다. 예를 들어 Word 변환, Git 상태 확인, OpenAI 문서 확인처럼 프로젝트마다 반복되는 작업은 기존 skill을 이용해 처리했습니다.

실제 예시:

- `doc-exporter`: Markdown을 DOCX/PDF로 내보내는 흐름 참고
- `git-ops`: 메인 repo와 서브모듈의 Git 상태 점검 및 커밋 범위 정리
- `openai-docs`: OpenAI API 관련 최신 문서 확인이 필요할 때 공식 문서 우선 확인
- `skill-creator`: Claude Code용 HWPX skill을 Codex 방식의 skill로 재구성할 때 사용

발표용 문장:

> “custom skill은 우리 프로젝트 규칙을 기억하게 하는 장치이고, 미리 만들어진 skill은 문서 변환이나 Git 점검처럼 반복되는 범용 작업을 빠르게 처리하는 장치로 사용했습니다.”

#### Playwright MCP와 브라우저 기반 테스트

Playwright는 두 가지 의미로 활용했습니다.

1. 제품 내부 기능
   - FastAPI의 크롤링 서비스가 Playwright로 네이버/카카오 리뷰 페이지를 열고 실제 리뷰 데이터를 수집합니다.

2. 개발 검증
   - 테스트할 때 Playwright MCP와 smoke script를 사용해 브라우저를 실제 사용자처럼 조작했습니다.
   - 회원가입, 로그인, 대시보드 진입, 리뷰 관리 탭 이동, 로그아웃 같은 흐름을 눈으로만 확인하지 않고 브라우저 자동화로 검증했습니다.
   - 실패 시 스크린샷을 남겨 어느 화면에서 문제가 생겼는지 확인할 수 있게 했습니다.

실제 구현/검증 근거:

- `pulse_python/app/services/crawler_service.py`: Playwright 기반 리뷰 수집
- `pulse_FE/scripts/playwright-smoke.mjs`: Chrome/Edge를 이용한 프론트 E2E smoke 테스트
- `.agents/context/WORKLOG_2026-04-08.md`: live auth/analysis/review-management 흐름 E2E 검증 기록

발표용 문장:

> “Playwright MCP는 단순히 테스트 코드를 돌리는 수준이 아니라, Agent가 브라우저를 실제 사용자처럼 조작하면서 로그인, 분석 조회, 리뷰 관리 흐름을 확인하는 검증 도구로 활용했습니다.”

#### 서브 에이전트 방식

긴 작업은 하나의 Agent가 모든 것을 동시에 기억하고 처리하기보다, 역할을 나누는 방식이 안정적입니다. 그래서 서브 에이전트는 “탐색 담당”, “구현 담당”, “검증 담당”처럼 나누어 생각했습니다.

활용 방식:

- 탐색형 서브 에이전트: 특정 기능이 어느 파일에 있는지 빠르게 찾고 요약
- 구현형 서브 에이전트: 정해진 파일 범위 안에서 코드 수정
- 검증형 서브 에이전트: 생성된 산출물이나 수정 결과를 별도 관점에서 확인

이번 HWPX skill에도 이런 관점이 반영되어 있습니다. `verify_hwpx.py`는 생성된 HWPX 문서를 별도 검수자가 확인하듯 구조 보존, XML 유효성, 원본 대비 손실 여부를 점검하는 도구입니다.

발표에서는 이렇게 말하면 좋습니다.

> “서브 에이전트는 여러 명의 개발 보조자를 동시에 쓰는 개념에 가깝습니다. 한쪽은 코드 구조를 찾고, 한쪽은 구현하고, 다른 한쪽은 검증하는 식으로 역할을 나누면 복잡한 기능에서도 실수를 줄일 수 있습니다.”

주의해서 말할 점:

- “Agent가 알아서 전부 했다”가 아니라 “사람이 역할과 검증 기준을 정하고 Agent들을 보조 작업에 배치했다”라고 말하는 것이 좋습니다.
- 실제 서비스 품질은 Agent 출력만 믿지 않고, 코드 실행과 Playwright/E2E 검증으로 확인했다고 강조하는 편이 안전합니다.

### 1-8. 발표에서 강조할 핵심 메시지

> “PULSE 개발에서 AI/Agent는 ‘대신 개발해주는 도구’라기보다, 사람이 방향을 정하면 코드 탐색, 초안 작성, 반복 검증을 빠르게 수행해주는 협업 파트너였습니다. 덕분에 짧은 기간에 프론트엔드, 백엔드, AI 서버가 연결된 실제 MVP 흐름을 만들 수 있었습니다.”

확장 문장:

> “여기에 custom skill, 미리 만들어진 skill, Playwright MCP, 서브 에이전트 역할 분리를 붙여서 Agent 활용을 일회성 대화가 아니라 반복 가능한 개발 프로세스로 만들었습니다.”

## 2. DSPy를 발표에서 어떻게 설명하면 좋은지

### 2-1. 한 문장 설명

> “DSPy는 프롬프트를 감으로 계속 고치는 대신, 입력과 출력 형식을 코드로 정하고 좋은 예시를 활용해 더 안정적인 프롬프트를 자동으로 구성하도록 돕는 도구입니다.”

교수님이 이해하기 쉬운 비유:

> “일반 프롬프트 작성이 매번 요리 레시피를 손으로 다시 쓰는 방식이라면, DSPy는 어떤 재료를 넣고 어떤 결과물이 나와야 하는지 표준 레시피 틀을 만들고, 좋은 예시를 참고해서 레시피를 자동으로 다듬는 방식입니다.”

### 2-2. PULSE에서 DSPy가 들어간 위치

DSPy는 홍보영상 생성 로직 중 “Veo에 전달할 프롬프트 계획”을 만드는 단계에 들어가 있습니다.

흐름:

1. 사용자가 페르소나, 영상 분위기, 품질 모드, 이미지, 콘셉트를 선택합니다.
2. 프론트엔드는 FastAPI의 프롬프트 추천/생성 API로 정보를 보냅니다.
3. FastAPI의 `PromotionPromptService`가 이 정보를 바탕으로 영상 프롬프트 계획을 만듭니다.
4. DSPy가 활성화되어 있으면, 정해진 입력 항목과 예시를 바탕으로 더 구조화된 프롬프트 JSON을 생성합니다.
5. 최종적으로 `PromotionVideoService`가 이 계획을 Veo용 텍스트 프롬프트로 바꿔 영상 생성 모델에 전달합니다.

관련 구현:

- `pulse_python/app/services/promotion_prompt_service.py`
- `pulse_python/app/services/promotion_video_service.py`
- `pulse_python/app/api/endpoints.py`
- `pulse_FE/src/features/promotion/PromotionPage.jsx`
- `pulse_FE/src/features/promotion/promotionApi.js`

### 2-3. DSPy에 넣는 입력값

PULSE의 DSPy 프롬프트 최적화는 단순히 “홍보영상 만들어줘”가 아닙니다. 아래 정보를 나누어 넣습니다.

- 타겟 페르소나: 어떤 손님을 겨냥하는지
- 영상 콘셉트: 어떤 메뉴나 장면을 보여줄지
- 영상 분위기: 에너지형, 프리미엄형, 감성형
- SNS 훅: 첫 2초에 무엇으로 시선을 잡을지
- 카메라/렌즈 가이드: 클로즈업, 매크로 렌즈, 얕은 심도 등
- 음식 중심 규칙: 영상이 다른 소재로 새지 않도록 제한
- 부정 프롬프트: 자막, 워터마크, 흐릿한 장면, 왜곡된 손 등 피해야 할 요소
- 이미지 분석 context: 업로드된 사진에서 읽은 음식 질감, 조명, 색감
- 레퍼런스 스타일 blueprint: 좋은 영상 예시가 있을 경우 그 구조

### 2-4. DSPy의 출력값

DSPy는 최종적으로 영상 생성 모델이 이해하기 쉬운 구조화된 계획을 만들도록 설계되어 있습니다.

출력 예:

- 영상 제목
- 해시태그
- 기본 스타일과 9:16 세로 영상 설정
- 핵심 장면 요소
- 피해야 할 요소
- 0-2초, 2-5초, 5-8초 타임라인

발표용 문장:

> “DSPy를 통해 프롬프트를 그냥 긴 문장 하나로 던지는 것이 아니라, 제목·해시태그·장면 타임라인·금지 요소까지 포함한 영상 기획안 형태로 정리했습니다.”

### 2-5. 그래서 뭐가 좋아졌는지

핵심은 성능 수치보다 “출력의 안정성”입니다.

1. 프롬프트 구조가 일정해졌습니다.
   - 매번 다른 말투로 프롬프트를 쓰는 대신, 입력과 출력 형식을 고정했습니다.

2. 페르소나 맞춤성이 좋아졌습니다.
   - 손님 분석에서 나온 페르소나, 태그, 추천 액션이 홍보영상 프롬프트에 들어갑니다.

3. 영상 생성 실패 위험을 줄였습니다.
   - 자막, 워터마크, 흐릿한 장면, 음식 왜곡 같은 요소를 negative prompt로 명시했습니다.

4. 메뉴 드리프트를 줄였습니다.
   - 예시나 레퍼런스에 끌려 엉뚱한 메뉴가 나오는 문제를 막기 위해, 생성 결과가 원래 콘셉트와 맞는지 검사합니다.

5. fallback이 있어 안전합니다.
   - DSPy에 필요한 레퍼런스 예시나 optimizer 파일이 없으면 무리하게 실행하지 않고, Gemini structured generation 또는 deterministic fallback으로 내려갑니다.

발표용 문장:

> “DSPy를 쓴 이유는 더 화려한 AI를 붙이기 위해서가 아니라, 영상 생성 프롬프트가 매번 흔들리지 않도록 입력·출력 규격을 고정하고, 페르소나 기반으로 더 일관된 홍보영상 기획안을 만들기 위해서입니다.”

### 2-6. 발표에서 너무 깊게 들어가지 말아야 할 부분

발표에서는 `Signature`, `ChainOfThought`, `LabeledFewShot` 같은 용어를 길게 설명하지 않는 편이 좋습니다.

대신 이렇게 풀어 말하면 됩니다.

- Signature: “입력과 출력 양식을 정한 것”
- ChainOfThought: “모델이 바로 답만 내는 것이 아니라, 전략을 한 번 정리하고 결과를 만들게 하는 방식”
- LabeledFewShot: “좋은 예시 몇 개를 참고하게 해서 결과 형식을 안정화하는 방식”
- Optimizer: “프롬프트를 사람이 계속 손으로 고치는 대신, 예시 기반으로 더 나은 프롬프트 구성을 찾아주는 장치”

### 2-7. 현재 구현 상태를 솔직하게 말하는 방식

현재 코드에는 DSPy 최적화 구조가 구현되어 있지만, 레퍼런스 blueprint나 사전 컴파일 optimizer 파일이 없을 때는 DSPy를 무리하게 실행하지 않고 fallback하도록 되어 있습니다. 이는 실패나 quota 낭비를 줄이기 위한 안전장치입니다.

발표에서는 이렇게 말하면 좋습니다.

> “현재는 DSPy 기반 프롬프트 최적화 구조를 홍보영상 생성 파이프라인에 넣어두었고, 레퍼런스 예시가 확보되면 few-shot 방식으로 프롬프트 품질을 더 끌어올릴 수 있게 설계했습니다. 예시가 부족한 상황에서는 fallback 프롬프트로 안정성을 우선합니다.”

## 3. PPT에 바로 넣기 좋은 1장 요약

제목:

> AI/Agent/Skill을 활용한 개발 방식과 DSPy 기반 프롬프트 최적화

핵심 메시지:

> 사람은 방향과 판단을 맡고, Agent는 탐색·초안·구현·검증을 반복 수행했습니다. 여기에 custom skill, Playwright MCP, 서브 에이전트 방식의 역할 분리를 더해 반복 가능한 개발 프로세스로 만들었습니다. 서비스 내부에서는 리뷰 분석과 홍보영상 생성에 AI를 적용했고, DSPy를 통해 홍보영상 프롬프트를 구조화했습니다.

왼쪽: 개발 과정에서의 AI/Agent 활용

- 문서 정리: 사업계획서, 발표 자료, 증빙자료 구조화
- 기능 기획: 사용자 흐름, 예외 상황, API 계약 정리
- 코드 탐색: FE/Spring/FastAPI 연결 흐름 추적
- 코드 제작: 리뷰 관리, 손님 분석, 홍보영상 프롬프트 API 구현 보조
- 반복 자동화: 빌드, 테스트, E2E, 문서 생성 자동화
- Git 보조: 서브모듈 상태와 변경 범위 정리
- custom skill: PULSE 전용 문서·Git·HWPX·제안서 작업 규칙 재사용
- Playwright MCP: 브라우저 기반 사용자 흐름 검증
- 서브 에이전트: 탐색, 구현, 검증 역할 분리

오른쪽: DSPy를 쓴 이유

- 프롬프트를 감으로 작성하지 않고 입력·출력 규격화
- 페르소나, 스타일, 이미지 context를 반영
- Veo가 이해하기 쉬운 영상 기획안 JSON으로 변환
- negative prompt와 콘셉트 검증으로 실패 가능성 감소
- 레퍼런스 예시가 쌓이면 few-shot 최적화로 품질 개선 가능

마무리 문장:

> “PULSE의 AI 활용은 단순히 생성형 AI를 붙인 것이 아니라, 개발 과정과 서비스 기능 양쪽에서 반복 작업을 줄이고 결과의 일관성을 높이는 방향으로 적용되었습니다.”

## 4. 발표 Q&A 대비

### Q1. AI가 코드를 다 짠 건가요?

아닙니다. 사람이 요구사항, 우선순위, 최종 판단을 맡았고 Agent는 코드 탐색, 초안 작성, 반복 수정, 검증을 보조했습니다. 특히 실제 서비스 동작은 코드 실행과 E2E 테스트로 확인했습니다.

### Q2. DSPy를 쓰면 영상 품질이 자동으로 좋아지나요?

DSPy 자체가 영상을 직접 좋게 만드는 것은 아닙니다. 대신 영상 생성 모델에 들어가는 프롬프트를 더 구조화하고 일관되게 만들어, 엉뚱한 결과나 흔들리는 출력이 줄어들도록 돕습니다.

### Q3. 현재 DSPy가 항상 실행되나요?

아닙니다. API 키와 레퍼런스 예시 또는 optimizer 파일이 있을 때 활성화됩니다. 조건이 부족하면 fallback 프롬프트로 동작합니다. 이는 quota 낭비와 불안정한 실패를 줄이기 위한 설계입니다.

### Q4. PULSE에서 가장 핵심적인 AI 활용은 무엇인가요?

리뷰 기반 고객 이해를 홍보 실행으로 연결하는 것입니다. 리뷰를 분석해 페르소나와 고객 여정을 만들고, 그 정보를 홍보영상 프롬프트와 리뷰 답변 생성에 다시 사용합니다.

### Q5. custom skill은 그냥 프롬프트 저장과 뭐가 다른가요?

단순 프롬프트 저장보다 범위가 넓습니다. skill에는 작업 절차, 주의사항, 사용할 스크립트, 검증 방식, 참고 문서 위치가 함께 들어갑니다. 그래서 Agent가 매번 새로 설명을 듣지 않아도 PULSE 프로젝트의 작업 방식을 재사용할 수 있습니다.

### Q6. Playwright MCP를 쓴 이유는 무엇인가요?

화면이 보이는 웹 서비스는 코드만 통과해도 실제 사용 흐름이 깨질 수 있습니다. Playwright MCP와 smoke script를 사용하면 로그인, 대시보드 진입, 리뷰 관리 이동 같은 흐름을 실제 브라우저에서 확인할 수 있어 UI/API 연결 문제를 더 빨리 발견할 수 있습니다.

### Q7. 서브 에이전트를 쓰면 무엇이 좋아지나요?

복잡한 작업을 한 번에 처리하지 않고 탐색, 구현, 검증으로 나눌 수 있습니다. 예를 들어 한 Agent는 관련 파일을 찾고, 다른 Agent는 제한된 범위의 코드를 수정하고, 또 다른 Agent는 결과를 검증하는 방식입니다. 이렇게 하면 긴 작업에서 놓치는 부분을 줄일 수 있습니다.
